# Understanding LLMs

*A guided lecture through language models and call_me_maybe project*

---

## Part 1 - How a Large Language Model Actually Works

### 1.1 Tokenization - text becomes numbers

A model cannot read letters. It reads **tokens**: integer IDs that stand for chunks of text (sometimes a whole word, sometimes a sub-word piece, sometimes a single character). This is done with a **tokenizer**, usually trained separately from the model itself using an algorithm like **Byte-Pair Encoding (BPE)** or **SentencePiece**.

- BPE starts from individual bytes/characters and iteratively merges the most frequent adjacent pairs into new tokens, until a fixed vocabulary size (e.g. 50,000-150,000 tokens) is reached.
- GPT-2-style BPE is *byte-level*: every possible byte value is mapped to a printable Unicode character first, so *any* input - including emoji, exotic Unicode, or raw binary - can always be encoded.

So `"Hello world"` might become `[15496, 995]` - a short list of integers.

### 1.2 Embeddings - numbers become meaning-vectors

Each token ID is looked up in an **embedding matrix**, turning it into a vector of hundreds or thousands of floating-point numbers. These vectors are *learned* during training so that tokens with similar meaning/usage end up close together in this high-dimensional space.

### 1.3 The Transformer - the actual "thinking" machine

The embeddings flow through a stack of **Transformer blocks**. Each block does two main things:

1. **Self-attention**: every token "looks at" every other token in the sequence and decides how much to weight their information when updating its own representation. This is what lets the model understand that "it" refers to "the dog" three words earlier, or that a variable name matches an earlier declaration.
2. **Feed-forward layers**: a per-token neural network that further transforms the representation.

Stack dozens of these blocks and you get a model that builds increasingly abstract representations of the input as depth increases.

### 1.4 The output - logits

After the last Transformer block, a final linear layer projects each position's vector back into a vector the size of the **entire vocabulary** - one raw score (a **logit**) per possible next token. This is what call_me_maybe: `get_logits_from_input_ids()` SDK call returns: a list of floats, one per vocabulary entry, representing "how much the model wants to produce this token next", *before* any probability normalization (softmax).

### 1.5 Autoregressive generation

An LLM produces text **one token at a time**:

1. Feed in the sequence so far.
2. Get logits for the next token.
3. Pick a token.
4. Append that token to the sequence.
5. Repeat.

This loop is why LLMs are called **autoregressive**: each new token is generated conditioned on everything generated before it (including its own earlier outputs).

### 1.6 Why this is a problem for "function calling"

A raw LLM has no built-in guarantee that its text output is syntactically valid - let alone valid *JSON matching a specific schema*. A 0.6B-parameter model (tiny, by industry standards) is especially prone to:
- forgetting to close a bracket or quote,
- inventing a function name that doesn't exist,
- putting a string where a number was expected,
- hallucinating extra fields.

This is the exact problem that call_me_maybe project solves.

## Part 2 - What "Function Calling" Means, and How call_me_maybe Solves It

**Function calling** is the general technique of getting an LLM to decide:

(a) which of a fixed set of tools/functions to invoke.
(b) with what arguments - based on a natural-language request.

There are two broad strategies for guaranteeing valid structured output from a language model:

1. **Prompt-and-parse**: ask the model to output JSON in free text, then try to `json.loads()` it, retrying or fixing on failure. Simple but fragile - a small model like Qwen3-0.6B will frequently break the format.
2. **Constrained (grammar-guided)decoding**: at *every single generation step*, mask out (forbid) any token that would make the output leave the space of valid answers. The model is never even offered the choice to produce broken output, because impossible tokens are removed from consideration before the model's top choice is taken. This is the approach call_me_maybe uses - the same core idea behind tools like llama.cpp's **GBNF grammars** and OpenAI's **Structured Outputs**.

Call_me_maybe project's key design insight, stated directly in its README, is:

> *"The pipeline never asks the LLM to produce raw JSON text… This removes the JSON-syntax failure mode entirely: the model can only ever influence values, never brackets, quotes, or commas."*

The JSON skeleton (`{"prompt": ..., "name": ..., "parameters": {...}}`) is never generated by the model at all - it's assembled afterward in Python via Pydantic models. The LLM is only ever asked narrow, type-constrained micro-questions.

## Part 3 - Walking Through call_me_maybe

### 3.1 The pieces, and how they connect

```
src/
├── __main__.py          entry point: wires everything together, handles errors
├── llm_sdk/              the provided wrapper around Qwen3-0.6B (HF transformers)
└── classes/
    ├── config.py         Init: env vars, default paths, CLI args (CliArgs)
    ├── constants.py       two shared regexes (numeric-token check, number-prefix check)
    ├── models.py          FunctionDefinition, FunctionCallResult, Vocabulary (pydantic)
    ├── decoder.py          ConstrainedDecoder - main piece of the project
    └── engine.py           FunctionCallEngine - orchestrates the whole run
```

Everything is a **Pydantic** `BaseModel` - this gives you automatic validation (e.g. malformed `functions_definition.json` throws a clear `ValidationError` instead of crashing obscurely later) and clean typed data flow between components.

### 3.2 `Small_LLM_Model` - the window into the model

This SDK class (in `llm_sdk/llm_sdk/__init__.py`) wraps Hugging Face's `transformers` library around `Qwen/Qwen3-0.6B`. It exposes exactly six methods, matching the pipeline from Part 1:

- `encode(text)` → tokenize text into `input_ids` (a tensor).
- `decode(ids)` → tokens back into text.
- `get_logits_from_input_ids(input_ids)` → the raw next-token logits.
- `get_path_to_vocab_file() / merges_file() / tokenizer_file()` → download the tokenizer's raw files, so we can build our own vocabulary map instead of relying on hidden internals.

Note: **no direct `torch`/`transformers` imports outside the SDK, and only the SDK's public methods are used** - never private attributes. This way it keeps the constrained-decoding logic testable and independent of the specific model-loading implementation.

### 3.3 `Vocabulary` - decoding GPT-2's byte-level alphabet

Here's what's really happening:

- The downloaded `vocab.json` maps token *strings* to integer IDs - but those strings aren't the real characters. GPT-2-style BPE first remaps every raw byte (0–255) to a "safe," printable Unicode character (so a literal space becomes `Ġ`, a newline becomes `Ċ`, etc.), *then* runs BPE merges on top of that remapped alphabet. This trick exists so that BPE, which is byte-oriented, never has to deal with unprintable or multi-byte characters directly.
- `_byte_decoder()` method reconstructs the **inverse** of that byte→Unicode mapping (following the same construction used in GPT-2's original tokenizer code), so that for every token in the vocabulary you can recover its true UTF-8 text.
- The result, `id_to_token`, is a dictionary from token ID → real text. This is essential because the constrained decoder needs to know, for every candidate token, *what actual characters it would add* to decide whether it's a legal continuation.
- `numeric_token_ids` is a precomputed subset (tokens whose text matches `^[\d.\-]+$`) used to speed up number generation - this way we don't have to scan the entire ~150K-token vocabulary on every step, just this smaller numeric-only slice.

### 3.4 `ConstrainedDecoder` - the core algorithm

This is where the valid output happens. It has three generation strategies, one per field type, plus one that dispatches between the string ones.

**a) `_generate_enum` - used for the function name and for booleans**

This is a **trie-walk over a small fixed set of candidate strings** (function names, or `["true", "false"]`):

1. Start with an empty `partial` string.
2. At each step, filter the vocabulary down to only tokens whose text, if appended, would still be a *prefix* of at least one candidate. (E.g. if candidates are `fn_add_numbers` and `fn_greet`, and `partial = "fn_"`, only tokens starting with something plausible like `add`, `greet`, etc. survive.)
3. Among the surviving tokens, take the one with the highest logit (this is where the model's actual "opinion", shaped by its training, still gets to decide *which* legal option to pick).
4. Stop the moment `partial` exactly equals one of the candidates.

This guarantees the function name (and booleans) can **never** be anything other than one of the pre-registered options - the model literally cannot hallucinate a function that doesn't exist.

**b) `_generate_number`**

Numbers don't have a small fixed candidate list, so instead:
- At each step, only tokens from the precomputed `numeric_token_ids` are considered, and only if appending their text keeps the whole string matching `^-?\d*\.?\d*$` (a valid number-in-progress: optional minus, digits, optional single decimal point, more digits).
- **Stopping condition**: rather than a fixed max length, at every step you also peek at what the model's *unconstrained* top choice would be - if that top choice would break the numeric format (e.g. add a letter, or a second decimal point), generation stops. In other words, the model itself signals "I'm done" by naturally wanting to write something non-numeric next (like a space or a period at the end of the answer).
- Finally, the accumulated string is parsed with `float(...)`.

**c) `_generate_string`**

Free text has no format constraint except *don't break out of the JSON string it will be embedded in*. So the only tokens forbidden outright are ones containing a `"` or a newline - everything else is legal. The same "peek at the unconstrained top choice" stopping trick is reused: if the model's natural next choice contains a quote or newline, stop. Afterward, stray leading/trailing quote or apostrophe characters are stripped.

### 3.5 `FunctionCallEngine` - orchestration

This ties it all together for each prompt:

1. Build a header prompt listing every available function with its description, ending in `"The function to call is: "`.
2. Encode it, call `select_function_name` to constrained-decode the function name (using the trie-walk).
3. Call `generate_parameters`, which walks the chosen function's parameter schema **in declared order**, and for each parameter:
   - appends a short sub-prompt like `Value for parameter "b" (number): ` to the **same growing token sequence** - each new sub-prompt is appended *after* the previous field's generated answer, the model has full context of what it already answered and won't just repeat the first number.
   - dispatches to `_generate_number`, `_generate_enum` (for booleans), or `_generate_string` depending on the schema's declared `type`.
1. Wraps everything into a `FunctionCallResult` Pydantic model - **this** is the actual guarantee of valid JSON structure, because `model_dump()` on a well-typed Pydantic object can never produce malformed JSON; the LLM was never given the opportunity to type a stray brace or comma in the first place.

### 3.6 `FunctionCallEngine.run()` - resilience

Each prompt is processed inside a `try/except`, so one bad prompt (or unexpected model hiccup) doesn't kill the entire batch - it's logged and skipped, and the run continues.

### 3.7 `__main__.py` - the entry point

`main()` does almost nothing except **wire the pieces together and handle three tiers of errors**:
1. `pydantic.ValidationError` → malformed `functions_definition.json`, reported field-by-field.
2. `(OSError, ValueError)` → missing files, invalid JSON, empty definitions.
3. A final catch-all, so the program *never* crashes with a raw traceback

## Part 4 - Putting It All Together

Prompt: `"What is the sum of 265 and 345?"`

1. Header prompt built, listing all 5 functions.
2. `select_function_name` walks the trie of `["fn_add_numbers", "fn_greet", "fn_reverse_string", "fn_get_square_root", "fn_substitute_string_with_regex"]` token-by-token, guided by logits, and lands on `fn_add_numbers`.
3. `generate_parameters` walks `{"a": number, "b": number}`:
   - sub-prompt `Value for parameter "a" (number): ` → constrained number decoding → `265.0`
   - sub-prompt `Value for parameter "b" (number): ` (appended *after* the "265" tokens, so the model has full context) → `345.0`
4. Result assembled:
```json
{"prompt": "What is the sum of 265 and 345?", "name": "fn_add_numbers", "parameters": {"a": 265.0, "b": 345.0}}
```

At no point did the raw LLM output a brace, quote, or comma - every one of those characters came from Python's `json.dump`, not from the model.
